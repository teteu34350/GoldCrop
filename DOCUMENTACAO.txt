GOLDCROP - DOCUMENTAÇÃO ATUALIZADA DO SISTEMA
=============================================

1. VISÃO GERAL
--------------

O GoldCrop é um sistema web de apoio à decisão para cafeicultura, desenvolvido em
Django com interface em HTML, CSS e JavaScript. O objetivo principal é auxiliar
produtores e equipes agrícolas a identificar janelas de aplicação mais favoráveis,
monitorar talhões, consultar clima local e acompanhar histórico operacional.

O sistema atual combina:
- autenticação real via Django Auth;
- páginas protegidas por sessão;
- dados de fazenda, talhões e perfil persistidos em modelos do Django;
- APIs internas para estado do sistema, perfil, talhões e aplicações;
- frontend em JavaScript para renderizar dashboards, calendário, mapa e modais;
- integração com Open-Meteo para previsão meteorológica e com Leaflet para mapa.

O produto está em estágio de protótipo funcional, com forte foco em experiência
visual e fluxo operacional de gestão agrícola.


2. STACK E TECNOLOGIAS UTILIZADAS
---------------------------------

- Python 3.x
- Django 6.1
- SQLite
- HTML + Django Templates
- CSS responsivo modularizado em static/styles.css

4. FLUXO DE AUTENTICAÇÃO E SEGURANÇA
-------------------------------------

O sistema usa autenticação real do Django. As páginas internas podem ser acessadas
apenas por usuários autenticados.

Fluxo principal:
- usuário acessa /login/
- informa e-mail e senha
- Django valida credenciais no backend
- em caso de sucesso, chama login(request, user)
- a sessão é criada e o usuário é redirecionado para /dashboard/

Páginas protegidas:
- /dashboard/
- /calendario/
- /talhoes/
- /fazenda/
- /sensores/
- /aplicacoes/
- /historico/
- /configuracoes/

Se não estiver autenticado, o sistema redireciona para /login/?next=... .

Além disso, os dados do usuário autenticado são injetados na página via:
- auth_user_data em base.html
- render do Django no template

6. FUNCIONALIDADES DE NEGÓCIO E LÓGICA DO FRONTEND
---------------------------------------------------

O frontend principal fica em static/app.js. Ele faz três coisas principais:

1. Carrega o estado do sistema via API do Django
2. Renderiza as páginas e seus componentes visuais
3. Gerencia eventos de interação do usuário

As principais estruturas de dados são:
- FARM: resumo da fazenda atual
- TALHOES_DATA: dados dos talhões
- HISTORICO_DATA: histórico de aplicações
- CAL_DATA: dados do calendário e recomendações
- TEAM_DATA: participantes da fazenda
- ACTIVITY_DATA: eventos de uso do sistema

O estado também dispõe de:
- selectedTalhaoRefId: ID do talhão selecionado para o contexto meteorológico
- talhoesMap: instância do mapa Leaflet
- currentPage: página ativa no momento


7. COMO FUNCIONA O MAPA E OS TALHÕES
-------------------------------------

Cada talhão pode incluir:
- nome
- área em hectares
- cultura
- variedade
- tipo de solo
- sensor
- latitude
- longitude
- raio em metros

O talhão selecionado com coordenadas válidas fornece o ponto para sua própria:
- consulta de previsão meteorológica via Open-Meteo
- análise e cálculo de janelas recomendadas
- exibição do clima no dashboard e calendário

O ID do talhão mantém separados coletas meteorológicas, recomendações,
planejamentos e aplicações. Trocar a seleção muda o contexto das telas; o
resultado de um talhão não é copiado aos demais. A escolha fica salva no
navegador.

Funções da seleção meteorológica:
- getUsableTalhoes()
- getSelectedReferenceTalhao()
- syncCalendarTalhaoSelector()

Se um talhão tiver latitude e longitude válidas, ele entra no mapa. Se não
tiver, permanece na listagem, mas não aparece no mapa e mostra que faltam
coordenadas para análise meteorológica.

No cadastro e edição, cada formulário possui um mapa próprio: clicar ou
arrastar o marcador preenche latitude e longitude somente daquele talhão. A
posição de outro talhão serve apenas como referência e nunca é aplicada
automaticamente. Talhões iniciais sem coordenadas precisam ser ajustados pelo
usuário; o sistema não inventa a localização nem o limite físico da área.

O mapa:
- é renderizado com Leaflet
- usa tiles do OpenStreetMap
- desenha um circleMarker para cada talhão geolocalizado
- desenha um perímetro em círculo ao redor do ponto central
- faz fitBounds quando há mais de um talhão no mapa

A camada visual usa cores por status:
- favorável: verde
- moderado: amarelo
- desfavorável: vermelho


8. COMO FUNCIONA O CALENDÁRIO E A IA
------------------------------------

A análise de recomendação é feita pelo motor GoldCropAnalysisEngine.js.

O processo é:
- o usuário seleciona um talhão
- o frontend consulta Open-Meteo para as coordenadas daquele talhão
- normaliza previsão atual, horária, diária e variáveis de solo estimadas por modelo
- o motor calcula índices, confiança, riscos e decisão para cada janela
- janelas com dados críticos ausentes (inclusive precipitação ou sua
  probabilidade) recebem INSUFFICIENT_DATA e não são exibidas
  nem persistidas como recomendação utilizável
- a melhor janela disponível alimenta o dashboard e o calendário daquele talhão

A estimativa de umidade de solo meteorológica não é uma leitura de SensorIoT.
Campos nulos continuam ausentes; não são convertidos em precipitação, temperatura
ou vento iguais a zero para criar uma recomendação.

Os dados podem ser carregados de duas formas:
- via mock local em JS, claramente indicado como modo demonstração
- via backend em /api/state/, que entrega clima e recomendações aninhados no
  respectivo talhão

No backend, o endpoint /api/state/ entrega:
- farm
- talhoes
- applications
- recommendations

O front usa recomendações do talhão selecionado. O campo top-level
recommendations continua existindo para compatibilidade com clientes antigos,
mas o fluxo individual da interface não usa recomendações sem associação ao
talhão ativo.


9. COMO FUNCIONA O CRUD DE TALHÕES
----------------------------------

End points disponíveis:
- POST /api/talhoes/
- PUT /api/talhoes/<id>/
- DELETE /api/talhoes/<id>/delete/

Funcionalidades:
- criar novo talhão com nome, área, cultura, latitude, longitude e raio
- atualizar dados do talhão inteiro ou parcialmente
- excluir talhão da fazenda atual
- validação no backend de coordenadas e valores numéricos

O formulário de cadastro inclui:
- nome do talhão
- área em hectares
- cultura
- latitude
- longitude
- raio aproximado em metros
- mapa para selecionar o centro aproximado de cada talhão individualmente
- marcadores dos outros talhões e aviso caso o ponto coincida com outro

Na tela Talhões, clicar no cartão ou marcador seleciona o registro, aproxima o
mapa da sua localização, abre um popup no marcador e atualiza o painel de
detalhes completo sob o mapa. O painel mantém as mesmas informações que antes
apareciam no modal: dados cadastrais, telemetria, localização, planejamento,
janela/IEA, clima, estado do sensor e histórico. Essa ação não abre o modal
"Janela de Ouro"; o modal continua acessível por outros atalhos. Nele, o
usuário pode visualizar:
- nome
- cultura
- idade
- solo
- sensor
- temperatura
- umidade
- coordenadas
- próximo planejamento
- histórico recente
- ações de editar e excluir


10. COMO FUNCIONA O PERFIL E A FAZENDA
--------------------------------------

O perfil do usuário pode ser atualizado pela rota:
- POST /api/profile/

Campos suportados:
- nome completo
- e-mail
- telefone

O papel do usuário não é editável no perfil: ele vem do vínculo persistido com
cada fazenda. A seleção da fazenda ativa é armazenada na sessão autenticada.

Equipe e acesso:
- MembroFazenda armazena usuário, fazenda, função e status ativo.
- Cada fazenda recebe um UUID interno e um código de acesso aleatório e único,
  distinto do identificador interno.
- O cadastro cria somente a conta e o perfil; não cria fazenda nem talhões.
- Uma conta sem fazenda é direcionada para `/fazendas/boas-vindas/`, onde pode
  criar uma fazenda ou entrar em uma existente pelo código.
- Quem cria a fazenda fica como Proprietário. Quem entra pelo código fica como
  Membro e recebe o mesmo acesso completo. O código tem formato
  `GCRP-XXXX-XXXX`.
- A restrição única `(fazenda, usuário)` impede vínculos duplicados.
- Pessoas vinculadas podem gerar outro código; o anterior deixa de ser válido.
- A troca de fazenda ativa persiste na sessão e cada consulta verifica o vínculo
  ativo antes de devolver dados daquela fazenda.
- Usuários autenticados sem vínculo são redirecionados ao onboarding em páginas
  protegidas; usuários já vinculados seguem diretamente para o dashboard.
- Não há convites por e-mail; o compartilhamento e a entrada na equipe usam o
  código da fazenda.
- NotificacaoFazenda persiste alertas operacionais e a leitura individual.

Funções autorizadas no servidor:
- Proprietário e Membro: ambos têm acesso completo para visualizar, planejar,
  registrar e gerenciar os dados da fazenda.
- A migração 0010 mantém como Proprietário o usuário criador e converte os
  demais vínculos existentes para Membro; códigos antigos são renovados.

Os dados do perfil são persistidos em:
- User do Django
- PerfilProdutor

Os dados da fazenda são alterados pela rota autenticada POST /api/farms/settings/.

12. FLUXO REAL DE USO DO SISTEMA
--------------------------------

Um fluxo típico de uso é:

1. usuário faz login
2. acessa dashboard e o sistema carrega fazenda e talhões ativos
3. seleciona um talhão (a seleção é mantida entre as abas)
4. se houver coordenadas, o sistema consulta clima e analisa somente esse talhão
5. dashboard e calendário mostram sua previsão e recomendação, ou declaram
   explicitamente que aguardam dados/que os dados são insuficientes
6. planeja uma aplicação para esse talhão; o planejamento aparece no calendário
7. registra a execução planejada ou registra uma aplicação diretamente
8. aplicação e histórico permanecem associados ao ID do talhão
9. seleciona outro talhão para analisar seu próprio clima e operações, sem
   herdar o IEA ou a recomendação anterior


13. ESTADO ATUAL DO PROJETO
---------------------------

O GoldCrop está em etapa funcional de protótipo com foco em operação. Os dados
operacionais mostrados nas páginas autenticadas são carregados do banco e não
há fazendas, talhões, equipe, histórico ou notificações de demonstração como
fallback. Se o servidor falhar, a interface mostra estado vazio/erro em vez de
substituir a resposta por registros inventados. Ele já possui:
- autenticação real em Django
- páginas protegidas
- cadastro de usuário separado da criação/entrada em fazendas
- onboarding para criar uma fazenda ou entrar pelo código
- cadastro e manutenção de talhões
- visualização de mapa georreferenciado
- calendário com recomendações
- painel dashboard
- painel de aplicações e histórico
- controle de perfil e dados da fazenda
- seleção de fazendas vinculadas à conta e acesso completo por membro
- código compartilhável de fazenda e notificações persistidas
- recuperação de senha com token Django e envio por e-mail

Ainda há pontos a evoluir, como:
- integração completa entre todos os módulos operacionais em tempo real
- definição de regras finais para cálculo do IEA por cultura e talhão
- sincronização mais detalhada entre recomendação meteorológica e execução
- expansão para sensores reais e rastreio em tempo real
- integração de sensores IoT reais e rastreio de telemetria em tempo real


14. COMANDOS ÚTEIS DE DESENVOLVIMENTO
-------------------------------------

Executar sistema:
python manage.py runserver

Validar projeto:
python manage.py check

Executar testes:
python manage.py test

Criar superusuário:
python manage.py createsuperuser

Configurar recuperação de senha por SMTP:
- EMAIL_HOST
- EMAIL_PORT (padrão 587)
- EMAIL_HOST_USER
- EMAIL_HOST_PASSWORD
- EMAIL_USE_TLS (padrão true) ou EMAIL_USE_SSL (padrão false)
- DEFAULT_FROM_EMAIL

Sem EMAIL_HOST ou DEFAULT_FROM_EMAIL, o backend retorna erro explícito para
redefinição de senha; não registra sucesso fictício.

Banco de dados em produção (Vercel):
- SQLite é usado apenas no desenvolvimento local; o filesystem da Vercel não é
  persistente nem gravável para armazenar o banco.
- Conecte um PostgreSQL gerenciado ao projeto Vercel. O projeto reconhece as
  variáveis DATABASE_URL, POSTGRES_URL e STORAGE_URL.
- Defina SECRET_KEY como variável de ambiente secreta na Vercel. DEBUG fica
  desativado por padrão nesse ambiente.
- As migrações Django são executadas automaticamente durante cada build da Vercel
  pelo `buildCommand` em vercel.json. Essa configuração prevalece sobre o
  comando definido no painel da Vercel e sobre `[tool.vercel.scripts]` em
  pyproject.toml.
- A base PostgreSQL será nova e não receberá automaticamente os dados do arquivo
  SQLite local; exporte/import seus dados separadamente se precisar deles.
